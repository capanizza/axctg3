Guia da nuvem do axctg3

Gerar versão nova · colocar na nuvem · acessar o banco · trocar o IP na Magalu
Versão do guia: 13/11/2026 (servidor rodando a versão 1.1.0)

Como ler este guia

Cada bloco de comando tem uma etiqueta dizendo onde ele deve ser digitado:

Windows PowerShell no seu PC    VM dentro da VM, depois de entrar por ssh    Navegador site ou console da Magalu

Regra do Linux que vale para a VM: comando que deu certo normalmente não diz nada; só o erro fala. As linhas em cinza que começam com # são comentários: não precisam ser digitadas.

Para colar no PowerShell, use o botão direito do mouse. Na janela do SSH (que também é o PowerShell), idem. Cuidado com linhas longas: se a colagem quebrar a linha, o pedaço final roda sozinho e dá erro. Na dúvida, cole uma linha de cada vez.

1. Preparar uma versão nova do axctg3

Resultado: um arquivo C:\axctg3-imagens\axctg3-X.Y.Z.tar, pronto para levar à nuvem.

Antes de começar

  • O código que vai para a nuvem está na branch main, com tudo commitado e os testes passando.
  • O Docker Desktop está aberto (ícone da baleia na bandeja do Windows, parado, sem animação).

Passo 1. Escolher o número da versão

Formato X.Y.Z. A versão no ar hoje é a 1.1.0. Sugestão:

  • só correções: aumenta o último número (1.1.0 → 1.1.1);
  • novidades: aumenta o do meio e zera o último (1.1.0 → 1.2.0).

Cada imagem gerada precisa de um número novo: o script recusa repetir. Para ver as versões já usadas:

Windows 
cd C:\projetos\jmix\axctg3
git tag

Passo 2. Ver se a versão nova altera o banco

Isso muda o plano de volta (seção 2, "Voltar para a versão anterior"). Troque v1.1.0 pela versão que está no ar:

Windows 
git log --oneline v1.1.0..HEAD -- src/main/resources/br/com/axialsoftware/axctg3/liquibase
  • Nada listado: sem alteração no banco; voltar de versão é simples.
  • Alguma linha listada: a versão nova altera o banco ao subir; voltar exige restaurar o backup. Anote isso.

Passo 3. Gerar a imagem

Windows 
cd C:\projetos\jmix\axctg3
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\gerar-imagem.ps1 -Versao 1.2.0

Leva alguns minutos (compila o projeto e monta a imagem). Termina com uma linha como:

==> Pronto: C:\axctg3-imagens\axctg3-1.2.0.tar (700 MB)

Passo 4. Marcar a versão no git

Registra exatamente qual código está dentro da imagem:

Windows 
git tag v1.2.0
git push origin v1.2.0

(Ou peça ao Claude para fazer a tag.)

Se der erro

MensagemO que fazer
A imagem axctg3:1.2.0 ja existeEsse número já foi usado. Escolha o próximo.
Erro falando de docker, pipe ou daemonO Docker Desktop não está aberto ou ainda está iniciando. Abra, espere a baleia parar e repita.
BUILD FAILEDO código não compila. Não continue: chame o Claude com a mensagem de erro.

2. Colocar a versão nova na nuvem

Durante a troca, o site fica fora do ar por um ou dois minutos (mostra 502). Faça num horário em que ninguém esteja usando.

Passo 1. Backup antes de tudo

Windows 
cd C:\projetos\jmix\axctg3
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\backup-nuvem.ps1
Get-Content C:\backups\axctg3-nuvem\backup.log -Tail 1

A última linha precisa dizer OK com a data e hora de agora. Se disser ERRO ou der Connection timed out, o IP de casa mudou: veja a seção 4 e só depois continue.

Passo 2. Enviar a imagem para a VM

Windows 
scp C:\axctg3-imagens\axctg3-1.2.0.tar ubuntu@201.23.79.163:~/axctg3/

Mostra o progresso e termina em 100%. Leva alguns minutos, conforme a velocidade de envio da sua internet.

Só quando o Claude avisar que a versão mudou também os arquivos da pasta deploy\nuvem (como aconteceu na troca para o Postgres 18), envie-os também: 
scp C:\projetos\jmix\axctg3\deploy\nuvem\docker-compose.yml ubuntu@201.23.79.163:~/axctg3/
scp C:\projetos\jmix\axctg3\deploy\nuvem\Caddyfile ubuntu@201.23.79.163:~/axctg3/
Para conferir você mesmo: git diff --stat v1.1.0..HEAD -- deploy/nuvem (nada listado = não precisa).

Passo 3. Entrar na VM

Windows 
ssh ubuntu@201.23.79.163

O cursor passa a mostrar ubuntu@axctg3teste:~$. A partir daqui, os comandos rodam na VM.

Passo 4. Carregar a imagem e trocar a versão

VM 
cd ~/axctg3
docker load -i axctg3-1.2.0.tar         # responde "Loaded image: axctg3:1.2.0"
docker images axctg3                    # a versão antiga continua lá: é o que permite voltar
sed -i 's/^AXCTG3_VERSAO=.*/AXCTG3_VERSAO=1.2.0/' .env
grep AXCTG3_VERSAO .env                 # tem que mostrar AXCTG3_VERSAO=1.2.0
docker compose up -d                    # recria só o app; banco e Caddy não são tocados

Passo 5. Acompanhar a subida

VM 
docker compose logs -f app

Espere aparecer Started Axctg3Application. Depois aperte Ctrl+C: isso só sai do log, o app continua rodando. Se aparecer APPLICATION FAILED TO START, vá para "Voltar para a versão anterior".

Passo 6. Conferir no navegador

Navegador

Abra https://axctg3.axialsoftware.com.br, entre e olhe o rodapé do menu lateral: tem que mostrar "Versão 1.2.0" com a data e hora em que a imagem foi gerada.

Passo 7. Limpeza

O disco da VM tem 20 GB. Apague o .tar (a imagem já foi carregada) e as versões mais antigas que a anterior (guarde sempre a anterior, para poder voltar):

VM 
rm axctg3-1.2.0.tar
docker images axctg3                    # lista as versões guardadas
docker image rm axctg3:1.0.1            # exemplo: só versões mais antigas que a anterior
exit                                    # sai da VM

Voltar para a versão anterior (rollback)

Se a versão nova não alterou o banco (passo 2 da seção 1 sem nada listado), basta repetir o passo 4 com a versão antiga:

VM 
cd ~/axctg3
sed -i 's/^AXCTG3_VERSAO=.*/AXCTG3_VERSAO=1.1.0/' .env
docker compose up -d
docker compose logs -f app              # espere "Started Axctg3Application"; Ctrl+C
Se a versão nova alterou o banco, a versão antiga pode não funcionar com o banco alterado. Voltar exige também restaurar o backup do passo 1, o que desfaz tudo o que foi gravado depois dele. Chame o Claude antes; a receita está no Apêndice.

3. Abrir o acesso ao banco da nuvem

O Postgres da nuvem só aceita conexões de dentro da VM. Para o exportador do Axial gravar os lotes de importação, abra um túnel SSH: a porta 5434 do seu PC passa a levar à porta 5432 dentro da VM.

Passo 1. Abrir o túnel

Windows 
ssh -N -o ServerAliveInterval=30 -L 5434:localhost:5432 ubuntu@201.23.79.163

Deixe a janela aberta. O cursor fica parado e nada aparece: isso é o normal, quer dizer que o túnel está ativo. Pode minimizar.

Passo 2. Usar

Rode o exportador do Axial normalmente: ele grava em localhost:5434. A primeira conexão do dia costuma demorar um pouco mais; não é travamento.

Passo 3. Fechar

Quando terminar, aperte Ctrl+C na janela do túnel.

O que cada parte do comando faz

ParteFunção
-NNão abre um terminal na VM, só cria o túnel.
-o ServerAliveInterval=30Manda um sinal a cada 30 s para a rede não derrubar o túnel enquanto a consulta lenta do Firebird roda.
-L 5434:localhost:5432A porta 5434 do PC leva à porta 5432 dentro da VM.
ubuntu@201.23.79.163Usuário e IP da VM.

Problemas comuns

SintomaO que fazer
Connection timed outO IP de casa mudou. Siga a seção 4.
Pede a senha da chave (passphrase)O ssh-agent do Windows perdeu a chave. Rode ssh-add uma vez e digite a senha.
O túnel caiu no meio da exportaçãoAbra de novo (passo 1) e exporte de novo: o exportador substitui o lote que ainda não foi importado.
bind ... Address already in useJá existe um túnel aberto na 5434, em outra janela. Use aquele ou feche-o.
Nunca abra a porta 5432 (banco) nem a 8085 (app) no grupo de segurança da Magalu. O acesso a eles é sempre pelo túnel.

Ver se a VM está de pé

Windows 
ssh ubuntu@201.23.79.163 "docker ps"

Tem que listar axctg3-caddy, axctg3-app e axctg3-postgres com (healthy).

4. Alterar o seu IP na Magalu

A porta 22 (SSH) da VM só aceita conexões do IP da sua casa. Esse IP é dinâmico: a operadora pode trocá-lo depois de queda de energia, troca de modem ou quando quiser.

Como saber que o IP mudou

  • ssh, scp e o túnel dão Connection timed out;
  • o backup diário falha: aparece ERRO no C:\backups\axctg3-nuvem\backup.log;
  • o site continua funcionando normalmente: as portas 80/443 são abertas para todos.

Passo 1. Descobrir o IP novo

Navegador

Abra https://api.ipify.org. A página mostra só o seu IP atual, por exemplo 187.106.242.87.

Passo 2. Criar a regra nova

Navegador
  1. Entre no console da Magalu Cloud e confira que a região selecionada é br-se1.
  2. Abra o grupo de segurança da VM axctg3teste (é o que tem as regras das portas 22, 80 e 443).
  3. Crie uma regra nova de entrada:
    DireçãoEntrada (ingress)
    ProtocoloTCP
    Porta22
    Origem (CIDR)o IP novo seguido de /32, por exemplo 187.106.242.87/32
    /32 quer dizer "só este endereço".
Na Magalu não dá para editar uma regra: cria-se a nova e exclui-se a antiga. Crie a nova primeiro. Excluir antes e errar um dígito tranca você para fora.

Passo 3. Testar

Windows 
ssh ubuntu@201.23.79.163 "echo ok"

Tem que responder ok. Se ainda der Connection timed out, confira o IP e o /32 da regra.

Passo 4. Excluir a regra antiga

Navegador

No mesmo grupo de segurança, exclua a regra da porta 22 com o IP antigo. Recarregue a página e confira que ela sumiu: já aconteceu de a exclusão não ser efetivada na primeira tentativa.

Passo 5. Recuperar o backup perdido

Se o backup diário falhou nos dias em que o IP estava errado, rode um agora e confira a linha OK:

Windows 
cd C:\projetos\jmix\axctg3
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\backup-nuvem.ps1
Get-Content C:\backups\axctg3-nuvem\backup.log -Tail 1
Nunca use 0.0.0.0/0 (o mundo todo) na regra da porta 22: robôs da internet ficam tentando senhas no SSH. As regras das portas 80 e 443 ficam como estão (0.0.0.0/0), porque o site é público.

Conferência opcional: como o resto do mundo vê a VM

Navegador

https://check-host.net/check-tcp?host=201.23.79.163:22 testa a partir de servidores em vários países: tem que dar Connection timed out na porta 22. Trocando :22 por :443, tem que conectar.

Apêndice: restaurar um backup na VM

Substitui o banco inteiro da nuvem pelo do backup: tudo o que foi gravado depois dele se perde. Use só para desfazer uma atualização que deu errado, e de preferência com o Claude acompanhando.

Troque <pasta> pelo nome da pasta do backup, por exemplo 20261113-095643.

Windows 
scp C:\backups\axctg3-nuvem\<pasta>\axctg3.dump ubuntu@201.23.79.163:~/axctg3/
scp C:\backups\axctg3-nuvem\<pasta>\arquivos.tgz ubuntu@201.23.79.163:~/axctg3/
ssh ubuntu@201.23.79.163
VM 
cd ~/axctg3
docker compose stop app
docker cp axctg3.dump axctg3-postgres:/tmp/base.dump
docker exec axctg3-postgres dropdb -U postgres axctg3
docker exec axctg3-postgres createdb -U postgres axctg3
docker exec axctg3-postgres pg_restore -U postgres -d axctg3 --no-owner /tmp/base.dump
docker exec axctg3-postgres rm /tmp/base.dump
docker run --rm -v axctg3_arquivos:/dados -v ~/axctg3:/origem postgres:18 sh -c "rm -rf /dados/* && tar xzf /origem/arquivos.tgz -C /dados"
docker compose start app
docker compose logs -f app              # espere "Started Axctg3Application"; Ctrl+C
rm axctg3.dump arquivos.tgz
exit

Para voltar também de versão, troque a versão no .env (seção 2, "Voltar para a versão anterior") antes do docker compose start app, e use docker compose up -d no lugar do start.
